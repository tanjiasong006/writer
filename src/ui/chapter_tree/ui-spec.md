# ChapterTree UI Specification v0.1

## 1. 目标

ChapterTree 是 Writer 左侧文档结构区的核心组件。

首要目标不是“漂亮”，而是：

- 快速识别文档结构
- 快速定位当前章节
- 低成本新建、重命名、删除章节
- 拖拽章节时明确知道最终落点
- 大量章节下仍保持稳定、清晰
- UI 行为与现有 ChapterTree Domain 模型严格对应

ChapterTree 不负责决定章节移动是否合法。

UI 只产生：

```ts
interface MoveIntent {
  chapterId: ChapterId
  targetChapterId: ChapterId
  position: 'before' | 'inside' | 'after'
}
```

Domain 层负责最终验证和执行。

# 2. 基本布局

单个章节节点采用一行布局：

```text
┌─────────────────────────────────────┐
│  ▾   4.2   实验方法             ··· │
└─────────────────────────────────────┘
```

元素顺序：

```text
缩进
↓
展开箭头
↓
章节编号
↓
章节标题
↓
弹性空白
↓
更多操作
```

建议节点高度：

```text
32px
```

可接受范围：

```text
30–34px
```

第一版统一使用：

```text
32px
```

---

# 3. 层级缩进

每增加一级：

```text
16px
```

例如：

```text
1 第一章

    1.1 背景

        1.1.1 国内研究

        1.1.2 国外研究

    1.2 方法

2 第二章
```

不要使用过大的缩进。

原因：

- Writer 可能存在较深章节
- 左侧栏宽度有限
- 深层章节仍需要给标题留下空间

---

# 4. 展开 / 折叠按钮

只有存在子章节时显示箭头。

展开：

```text
▾
```

折叠：

```text
›
```

按钮点击区域：

```text
20 × 20 px
```

箭头本身可以较小。

重要：

```text
点击箭头
→ 只切换展开状态，不改变当前章节

点击章节标题区域
→ 只切换当前章节，不展开 / 收起
```

两者不能混用：箭头不做选中，标题不做展开 / 收起。

没有子节点时，仍保留与箭头相同宽度的占位区域，保证标题对齐。

---

# 5. 章节编号

编号示例：

```text
1
1.2
3.4.1
```

编号和标题之间：

```text
6–8px
```

编号视觉权重低于标题。

例如：

```text
4.2    实验方法
```

而不是：

```text
4.2 实验方法
```

编号颜色可稍弱。

---

# 6. 标题

默认：

```text
单行
超出宽度 → ellipsis
```

例如：

```text
4.2  这是一个非常非常长的章节标题……
```

不要自动换行。

否则：

- 树高度不稳定
- 拖拽目标尺寸不断变化
- 大文档阅读效率下降

鼠标停留在截断标题上时，可通过 tooltip 显示完整标题。

---

# 7. 默认状态

默认节点：

```text
背景透明
文字普通
无边框
更多按钮隐藏
```

例如：

```text
   ›  3.2  原料准备
```

尽量保持安静。

章节树应该首先呈现“结构”，而不是呈现大量按钮。

---

# 8. Hover 状态

鼠标进入一行后：

```text
浅背景
显示 ···
```

例如：

```text
┌─────────────────────────────────────┐
│  ›  3.2  原料准备               ··· │
└─────────────────────────────────────┘
```

Hover 不应该比 Selected 更醒目。

---

# 9. Selected 状态

当前正在编辑的章节必须非常容易识别。

推荐：

```text
浅背景
+
左侧 2px 或 3px 强调条
+
标题稍微加重
```

例如：

```text
▌  ▾  4.2  实验方法
```

不要仅通过改变文字颜色表示选中。

原因：

长时间写作时，用户会频繁在：

```text
章节树
正文
章节树
正文
```

之间切换。

需要一眼确认：

> 当前正文属于哪个章节？

---

# 10. Selected + Hover

选中章节 hover 时：

```text
保持 selected 主视觉
仅增加 ···
```

不要突然换成完全不同的 hover 样式。

---

# 11. 拖拽手柄

第一版建议：

```text
整个节点可拖拽
```

而不是必须抓取独立拖拽手柄。

原因：

章节树主要用于结构编辑，整行拖拽更自然。

后续如果发现误拖问题，再增加：

```text
⋮⋮
```

形式的 drag handle。

---

# 12. 拖动中的源节点

开始拖拽后：

源节点：

```text
opacity ≈ 0.4–0.6
```

但仍保留原位置。

不要立即从树中消失。

否则用户容易失去：

```text
“我是从哪里拖出来的”
```

这一上下文。

---

# 13. Drag Preview

拖动时显示一个轻量浮层：

```text
┌──────────────────────┐
│ 4.2 实验方法          │
└──────────────────────┘
```

不需要复制完整章节树节点 UI。

只需要：

```text
章节编号 + 标题
```

# 14. Drop Position

这是 ChapterTree 最关键的 UI。

必须明确表达：

```text
before
inside
after
```

三种语义。

---

## 14.1 Before

鼠标位于目标章节上部区域时：

```text
─────────────────────
4.2 实验方法
```

显示一条水平插入线。

语义：

```ts
position: 'before'
```

---

## 14.2 Inside

鼠标位于目标章节中部时：

```text
┌─────────────────────┐
│ 4.2 实验方法         │
└─────────────────────┘
```

整行或主要内容区域出现明确高亮。

语义：

```ts
position: 'inside'
```

即：

> 将拖动章节作为目标章节的子章节。

---

## 14.3 After

鼠标位于目标章节下部时：

```text
4.2 实验方法
─────────────────────
```

显示水平插入线。

语义：

```ts
position: 'after'
```

---

# 15. Drop Target 区域划分

节点高度：

```text
32px
```

建议拆成：

```text
0–8px      before
8–24px     inside
24–32px    after
```

即：

```text
25% / 50% / 25%
```

Inside 区域稍大。

因为：

```text
before / after
```

依赖精确位置；

而：

```text
inside
```

应该容易命中。

---

# 16. Drop Indicator

Before / After 插入线不要只和当前节点一样宽。

最好根据最终层级显示正确缩进。

例如把：

```text
3.2
```

拖到：

```text
4.1
```

下面作为同级：

```text
    4.1 原料
    ───────────────
    4.2 工艺
```

插入线的位置应该隐含：

```text
最终层级
```

而不是永远从树最左边开始。

这会显著增加拖拽的可理解性。

---

# 17. 非法 Drop

如果 Domain 可以预判当前移动无效：

例如：

```text
把章节拖入自己的子孙节点
```

UI 应：

```text
不显示合法 drop indicator
```

或：

```text
显示禁止 cursor
```

不推荐：

```text
先显示正常落点
→ 松手
→ 再提示失败
```

如果 UI 无法提前判断，则允许 Domain 拒绝，但失败后树必须保持原状。

# 18. 展开行为与拖拽

用户把章节拖到一个折叠节点的 `inside` 区域，并停留约：

```text
500–700ms
```

可以自动展开该节点。

这属于第二阶段增强功能。

第一版不实现也可以。

```text

节点菜单 ··· → 重命名

菜单栏 章节 → 重命名章节

⌘↩（只在章节树中有效）
```

# 21. 新章节默认位置

推荐规则：

当前章节存在时：

```text
“新增章节”
→ 当前章节之后
```

“新增子章节”：

```text
→ 当前章节最后一个子节点
```

如果没有当前章节：

```text
→ 文档根节点末尾
```

这个行为以后应该始终保持稳定。

# 22. 新建后的行为

新建章节后：

```text
自动选中
+
自动进入标题编辑状态
```

例如：

```text
3.4  [未命名章节________]
```

用户只需开始输入。

不要：

```text
新建
→ 再找到章节
→ 再重命名
→ 输入标题
```

# 23. 删除

删除属于危险操作。

节点菜单：

```text
删除章节
```

如果章节：

```text
无子节点
+
内容为空
```

可以考虑直接删除。

如果：

```text
存在正文
或
存在子章节
```

必须确认。

确认内容应明确告诉用户：

```text
删除章节“实验方法”？

该章节包含正文以及 3 个子章节。
```

**当前决定：** 没有子章节、没有正文（空白字符不算正文）且没有被其他章节引用的章节直接删除，不显示确认；
否则先确认，说明按内容给出。被引用时另说明其他章节中指向它（包括子章节）的引用数量，删除后这些引用失效
（docs/decisions.md 第 9 节）。
节点菜单、右键菜单、菜单栏"删除章节"与 ⌘⌫（Windows：Ctrl+Delete，只在章节树获得焦点时有效）走同一规则。
单独的 Delete / Backspace 不删除（§29）。直接删除后焦点落在删除后选中的章节上；从正文经菜单栏删除时焦点留在正文。

确认对话框是模态的：打开时焦点在"取消"，焦点所在按钮始终有描边；Tab / ⇧Tab 在两个按钮间循环，Esc 取消。

**撤销删除（2026-10-03）：** 删除后正文区底部提示“已删除“标题””并带“撤销”（8 秒后消失）；章节树获得焦点时
⌘Z（菜单栏“编辑 → 撤销删除章节”）同样撤销。撤销把最近一次删除的章节连同子章节与正文放回原来的父章节与位置并选中它
（原父章节已不在时放到根层级末尾），之后的其他修改保留；可以连续撤销多次删除，不提供重做，记录不持久化。
其他结构操作（新建、移动、重命名）仍不能撤销。

# 23.1 写作状态与备注（2026-10-03）

节点菜单在“移动”之后有“状态”（无 / 草稿 / 待修改 / 完成，当前打勾）与“添加备注… / 编辑备注…”。
标题之后依次显示备注图标（有备注时，悬停显示内容）与状态圆点（7px：草稿空心、待修改橙色、完成绿色），
都比标题弱，长标题截断时它们保留在行尾。docs/decisions.md 第 16 节。

# 27. 滚动行为

章节树自身滚动。

不要让整个 Writer 页面跟着章节树滚动。

布局：

```text
┌────────────────┬──────────────────────────┐
│ Chapter Tree   │ Editor                   │
│                │                          │
│ scroll         │ scroll                   │
│                │                          │
└────────────────┴──────────────────────────┘
```

两边滚动独立。

---

# 28. 当前章节自动可见

当已有的其他入口切换当前章节后，章节树应让当前章节自动可见。
本规则不要求新增搜索或内部链接能力；未来具备这些入口时适用同一行为。

例如：

```text
搜索
内部链接
```

全文阅读中滚动到的章节成为当前章节，同样适用本规则（旧的全文预览已移除）。

章节树应：

```text
展开对应祖先节点
+
自动滚动到当前章节
```

但避免强烈跳动。

建议：

```ts
scrollIntoView({
  block: 'nearest'
})
```

而不是强制居中。

# 29. 键盘交互

第一阶段至少预留：

```text
↑
选择上一可见章节

↓

选择下一可见章节

Enter
进入当前章节

Esc
退出编辑
```

暂时不要让：

```text
Delete
```

直接删除章节。

误删风险太高。

当前实现（快捷键只用"⌘ + 一个键"，定义见 `src/ui/common/shortcuts.ts`）：

```text
章节树中
  ↑ ↓ Home End ← →   浏览、展开 / 折叠（h j k l 等同 ← ↓ ↑ →）
  Enter              进入正文
  ⌘N                 在其后新建同级章节，随即编辑标题；Enter 确认后留在章节树（与重命名相同）
  ⌘↩                 重命名
  ⌘↑ / ⌘↓            上移 / 下移
  ⌘← / ⌘→            升级 / 降级
  ⌘⌫                 删除（空章节直接删除，否则先确认，见 §23）
  ⌘/ 或 Shift+F10    章节菜单

任何位置
  ⌘J                 在章节树与正文之间切换（侧栏隐藏时先显示）
```

这些 ⌘ 快捷键只在章节树获得焦点时作用于章节：正文中 ⌘N 不做任何事，⌘↩、⌘ + 方向键、⌘⌫ 保持编辑器自己的含义
（响应链，见 `app_shell/app_menu.ts`）。

# 30. 焦点状态

键盘操作时，需要明确 Focus。

Selected 和 Focus 是两个概念：

```text
Selected
= 当前正文章节

Focus
= 当前键盘操作节点
```

第一版两者可以经常重合，但数据模型不要强制绑定。

用户必须随时看出键盘在章节树还是正文（macOS 侧栏的惯例）：

```text
焦点在章节树   选中行：强调色底 + 强调条；焦点行有描边
焦点在正文     选中行：灰色底 + 灰色条（仍加粗，当前章节仍一眼可见）；正文中光标闪烁
```

不给整个面板加边框或改背景色。

鼠标点在章节树的任何位置（标题、行内空白、编号、箭头、行间、树下方空白）都让章节树获得焦点：
焦点落在被点的行，点在行外时落在可 Tab 聚焦的行。鼠标激活不显示焦点描边。

# 36. 一个核心原则

ChapterTree 的 UI 不应该自己重新定义章节规则。

结构：

```text
Pointer / Keyboard
        ↓
ChapterTree UI
        ↓
MoveIntent
        ↓
Application
        ↓
Domain moveChapter()
        ↓
new ChapterTree
        ↓
render
```

UI 只负责：

```text
“用户想做什么”
```

Domain 负责：

```text
“这件事是否合法，以及执行后的树是什么”
```

不要把：

```text
祖先判断
子孙判断
index 修正
层级限制
树结构修改
```

重新写进 React / UI 组件。

---

# 37. 第一版验收标准

用户应该可以在不思考规则的情况下完成：

```text
新建 5 个章节
↓
创建 2 层子章节
↓
展开 / 折叠
↓
修改标题
↓
调整章节顺序
↓
把章节拖进另一个章节
↓
再拖出来
↓
删除章节
```

整个过程中：

- 不需要猜测拖拽会落在哪里
- 不会意外修改树结构
- 当前正在写哪个章节始终明确
- 树结构变化后视觉结果立即符合预期

达到这一点，ChapterTree 第一版就算真正完成。
