# 产品与技术决策

已确定、需要长期保持的决策。修改任何一条前，先与产品负责人确认并更新本文件。

## 1. 正文文件名

正文文件名由章节编号决定（`content/ch_2_1.md`），ChapterId 是稳定内部身份。
编号变化时文件必须重命名，一致性由 persistence 层的保存事务保证。
详见 `docs/project-format.md` 第 2、5 节。**不得改用 ChapterId 作为文件名。**

## 2. 编辑器

- 用户编辑的是结构化正文，而不是 Markdown 源码。不以"源码编辑器"为产品方向，也不要求用户理解 Markdown。
  （早期 MVP 使用 CodeMirror 6 做 Markdown 源码编辑，已整体迁移到 ProseMirror，不保留源码编辑模式。）
- ProseMirror 是正文编辑器的内部文档模型和交互内核；schema（`ui/editor/schema.ts`）是正文结构的权威定义。
- 后续正文编辑能力优先基于 ProseMirror schema / command / plugin 扩展，而不是通过 Markdown 文本操作实现。
- Markdown 继续作为正文的持久化格式；领域模型（正文是 Markdown 字符串）、正文磁盘格式及 Rust 导出内容解析保持不变。
  Markdown ⇄ ProseMirror 文档的转换只发生在编辑器层（`ui/editor/markdown.ts`）。
- Markdown 方言与导出的 pulldown-cmark 一致：CommonMark + GFM 表格、删除线、任务列表；原始 HTML 视为文字。
- schema 只包含 Markdown 能保存、且 Rust 渲染器能渲染的结构；不能用 Markdown 保存的能力（合并单元格、
  单元格内多段落、列宽等）不进入编辑器。需要新增此类能力时，先与产品负责人确认是否调整持久化格式。
- 提供常用操作入口：图片、表格、列表、粗体、斜体、引用、代码块；另有 Markdown 风格的输入规则作为快捷输入。
- 编辑器不得对未编辑的正文做任何规范化；只有用户真正修改的章节才会被写回（编辑后又撤销回原样时写回原文）。
  被修改的章节按统一风格整体重新写出，渲染结果不变；CRLF、BOM、结尾是否换行保持原文件的风格。

## 3. 章节标题与正文

- 章节标题只存在于文档结构（manifest）中，Markdown 正文不重复保存章节标题。
- 章节编号不存入正文，也不存入 ChapterNode；编号永远由树结构推导（`chapter_numbering`）。
- 编辑展示和导出时根据章节树深度和编号生成章节标题。

## 4. 保存

- 自动保存（防抖）+ Cmd/Ctrl+S 手动保存。
- **dirty 状态的边界**：只有当存储层明确返回"本次保存已提交"时，才把
  "发起保存时的那份快照"标记为已保存。
  - 保存失败（无论在提交点前还是后）→ 文档保持 dirty，错误对用户可见，之后会重试。
  - 保存进行中用户继续编辑 → 保存成功后文档仍为 dirty（新编辑不属于那份快照）。
  - 同一时间最多一个保存在进行；期间的保存请求合并为之后的一次保存。
- 关闭窗口时若仍为 dirty，先尝试保存；保存失败必须让用户选择，不能静默丢弃。

## 5. 导出

- **能力边界：Writer 负责组织和编辑结构化文档与内容，并生成整洁、可靠的交付文档；不负责后续的精细排版。**
- Word 用于交给他人继续编辑：优先保证内容完整、结构清楚、段落样式规范、便于后续修改，
  不承诺不同 Word / WPS 环境中的折行、分页完全一致。需要精细排版时，导出 Word 后在其他工具中处理。
- Word 的正文、标题与图注使用对应的内置样式（如 Normal、Heading1–9、Caption），标题带正确的大纲层级，
  使接收者能统一修改样式、使用导航窗格与生成目录；不以逐段直接格式代替这些语义样式。
- PDF 用于直接阅读、打印和正式交付：Writer 负责自动排版的页面质量，保证内容可读、无溢出或遮挡，
  接受合理留白，不保证每一页满足特定构图要求。
- 编辑展示、Word 输出与 PDF 排版职责独立：内容与结构必须一致，不要求字体、版心、折行、分页或图片显示尺寸一致。
- Word / PDF 导出随 Writer 自带，**不依赖用户安装 Pandoc 或 LibreOffice**。
- Word：Rust `docx-rs` 生成。
- PDF：优先内嵌 Typst（实现方案，不是产品约束）。若发现明显的跨平台、体积或字体问题，
  先与产品负责人沟通再调整。
- Word 与 PDF 共用同一个 Markdown 解析器及内容中间模型（Rust `pulldown-cmark`）；
  编辑器使用自己的 Markdown 转换实现，内容与结构一致性由跨实现契约测试保证。

## 6. 字体

- 字体按"字体族"配置：衬线（宋体类）、无衬线（黑体类）、等宽；每个字体族是一个有序的候选字体列表（fallback 链），
  同时包含拉丁字体与中文字体，覆盖 macOS / Windows / Linux 的常见字体。Word 默认样式与 PDF 文档级排版
  为正文、标题、引用、图注等元素选择衬线或无衬线；等宽用于代码。编辑展示默认可复用这些候选，
  但不受输出字体族范围约束。
- 选择字体时按列表顺序使用第一个可用的字体，逐字形回退。
- 预留"随应用打包字体"的位置：打包字体始终参与查找，未来可放入开源中文字体保证一致性。
- 找不到任何可显示中文的字体时，导出给出明确警告，而不是静默输出缺字。
- 输出字体候选配置集中在一处（Rust `export::fonts`），不在各导出器里各写一份。
  编辑展示可以复用字体候选，但不因复用而与导出样式绑定；当前 CSS 字体栈与 Rust 一致的实现不作为长期绑定要求。
- PDF 排版设置中的字体选择限于可可靠输出的受控字体族，不提供任意系统字体列表。
- 编辑环境字体不受输出字体族范围限制，可以使用本机字体；是否提供系统字体选择入口另行设计。
  编辑字体不进入项目或输出请求，不因此承诺跨机器一致。
- 打包字体：把 .ttf / .otf / .ttc 放入应用资源目录下的 `fonts/`（Tauri `bundle.resources`）即参与 PDF 排版的字体查找；
  要让它成为首选，把它的字体族名加到 `export::fonts::families` 对应字体族列表的前面。
  Word 只写字体名，由用户机器上的 Word 负责替换。

## 7. 稳定性

- release 构建使用 `panic = "unwind"`：第三方排版库（Typst、docx-rs）遇到异常输入时 panic 只让本次导出失败，
  不会让整个应用退出。导出在后台线程执行，panic 被转换为普通错误返回给界面。
- 来自用户项目的数据（图片、正文）中的任何问题都不能让应用崩溃：图片解码带尺寸 / 内存上限，
  失败时以占位文字输出并在导出报告中列出。

## 8. 内容与排版分离（编辑展示与自动排版）

- **Markdown 是正文内容的持久化格式，不承担完整排版语言的职责。** 正文只表达"这是什么"（段落、标题、列表、引用、
  代码、表格、图片、图注等），由 Markdown + ProseMirror schema 表达。
- **编辑阶段只关注内容**：提供默认美观、易读的展示，不提供输出排版设置入口，不以最终页面效果为编辑目标。
  粗体、斜体、标题、列表等正文表达能力继续保留。
- **“主题”指编辑环境主题，属于应用级偏好**：用于调整编辑环境的视觉与阅读体验，不是文档样式，
  不随项目保存，不改变正文、不产生文档 dirty 状态，也不影响 Word / PDF 输出。
  具体可调整项在后续设计时确定；开发版与正式版的主题偏好遵循应用状态隔离规则。
- **解除一份主题同时控制编辑界面、Word 与 PDF 的绑定**。Word 提供规范的默认输出样式；
  PDF 在排版阶段提供少量文档级配置，称为排版配置，不复用编辑环境主题的概念。
  具体配置项与默认值在后续实现时确定。
- **PDF 采用规则驱动的自动排版**：文档级配置随项目保存并复用，排版始终基于当前正文，
  不维护另一份可独立编辑的内容。内容变化后重新计算页面，正式交付前检查更新后的结果。
- **不提供针对特定内容元素的手工排版或局部布局覆盖**：包括单张图片尺寸 / 对齐 / 独占一页、
  单个段落间距、手工分页、固定页码位置和页面坐标调整。图片、图注、表格等按统一规则自动安排。
  不为这些排版设置引入元素实例身份。未来扩展此边界须先与产品负责人确认。
- **图片大小、对齐、位置等展示 / 布局信息不属于文档内容或文档元数据**，不为单张图片保存这些设置，
  也不转移到 Markdown、资源文件 metadata 或另一份局部布局配置中。
  编辑展示按统一规则适应编辑区，Word / PDF 按各自的统一排版规则适应输出区域；图片引用与图注仍属于内容。
- 标题跟随正文、图片与图注保持在一起、图片适应页面、跨页表头重复等由排版引擎处理。
  不理想的页面优先通过改善通用规则解决，不要求用户逐页维护；最终输出需可检查，
  通过导出 PDF 后在外部阅读器中检查，当前不提供应用内预览。
- **不因为新增视觉能力默认扩展 Markdown 方言**（例如 `{width=60%}`、`<span style>`）。如果未来某项核心文档语义
  无法由 Markdown 表达，由产品负责人决定是否扩展 Markdown 或改变存储模型。
- 排版配置随正常的项目保存事务提交，不引入第二套保存流程，不进入正文或正文撤销历史。
  排版使用语义参数（字体族、磅值、倍数等），Rust 不理解前端 CSS。

### 图片自动尺寸约束

- 保持宽高比，统一规则下小图不放大，宽图缩到可用宽度，竖长图同时受可用高度限制。
- 独立图片按完整页面正文区域的可用宽、高计算尺寸上限；有图注时为图注及必要间距预留空间。
  尺寸与图片落在页上的位置无关，不按当前页剩余空间缩小图片。
- PDF 当前页空间不足时将图片与图注整组移到下一页，不为塞进页底压缩图片；
  仅当完整页面的正文区域或图注占用空间改变时重新计算尺寸，不挤占页眉页脚或裁掉内容。
- Word 按写入的纸张、页边距及图注空间计算尺寸上限，并表达图片与图注保持在一起的约束；
  实际分页由 Word / WPS 完成，Writer 不依据其运行时剩余页面空间调整图片尺寸。
- 行内图片受所在容器的可用宽度限制（例如表格单元格），同时保持比例、不放大，
  在分页输出中仍受完整正文区高度上限限制；不默认按文字行高压成小图。
  表格单元格的可用宽度按列数等分正文宽度、再减去单元格左右内边距（Word 使用默认的 108 twip，
  PDF 使用 6pt）。PDF 中没有图片的表格列宽仍随内容；含图片的表格各列等宽（与 Word 相同），
  表头高度按与最终表格相同的列宽、在表格实际所在容器的宽度下测量。
  列表与引用中的图片同样受缩进后的可用宽度限制。
  表格中含图片的行不能跨页拆开，而表头在每页重复：正文行中的图片高度不超过正文区减去表头高度与
  单元格上下间距；表头中的图片不超过正文区高度的四分之一，避免重复的表头占满页面。
- 预留空间的计算：PDF 在排版时实际测量图注与表头的高度（按实际字体、宽度与折行），不做估算；
  Word 的排版结果无法在导出时测量，按折行上限保守估计（每个字符按 1em、按单词贪心折行），
  预留偏大只会让图片略小，不会让图注或图片被挤出正文区。
  不设最小显示宽度：极窄的长图宽度可以小于 1pt，高度上限优先。
- 图片固有物理尺寸如何解释 DPI、缺少 / 异常 DPI 时的回退值仍待确定；
  实施统一尺寸算法前须明确该策略，并覆盖高分辨率截图、无 DPI、小图与竖长图用例。
  不以图像元数据直接覆盖页面边界限制，也不把 DPI 转成单图布局设置。
- 待评估的 DPI 方案：PNG / JPEG 元数据在 72–600 DPI 范围内时按其换算，缺失或异常时按 96 DPI。
  这是候选方案，不作为已确认算法；实现前检查横纵 DPI 不一致、解码后元数据保留和跨格式行为。
- 当前实现（`export::images`、`export::pdf`、`export::docx`）：页面边界、图注与表头预留、容器宽度与"不放大"规则已落实；
  图片固有尺寸仍按移除旧样式前的固定 96 DPI 换算，不读取图像元数据。DPI 策略确定后只需替换这一换算。

### 移除预览（已完成）

- 移除应用内全文 HTML 预览，不新增应用内 PDF 分页预览；取消预览按钮、菜单、工作区模式切换、
  预览章节点击选择与滚动同步、预览刷新状态和相关偏好。章节树与单章编辑继续承担内容导航。
- 应用内连续展示“章节标题 + 自动编号 + 全文正文”的阅读入口一并取消，不转移到编辑器，
  不在本次修改中创建替代视图。全文通读与最终页面检查通过导出文件在外部阅读器中进行，
  外部阅读器不接替 Writer 内部的章节选择、焦点和滚动同步。
- 移除 `DocumentPreview.vue`、预览 composable、Application / Infrastructure 的预览端口与调用、
  Rust `render_preview` command 和仅供预览使用的 HTML 渲染模块及相关测试 / Story。
  保留 Word / PDF 使用的 Markdown 解析、IR、章节请求组装与资源安全解析，避免随预览一并删除。
- `RenderRequest` 移除 `theme`、`images`，只携带文档标题及按阅读顺序展开的章节内容与结构；
  Word / PDF 各自取得默认输出参数，未来 PDF 配置独立传入，不恢复共享主题。
- 之前“HTML 预览暂用编辑默认参数”的过渡规则取消，移除预览不以新主题或 PDF 配置为前置条件。
  未来重新引入任何应用内预览需单独确认产品需求。
- 外部阅读器检查的操作成本需要评估；候选方式包括导出成功后“打开文件”，
  或按需生成到临时目录并用系统阅读器打开。两者均未确定，不随预览移除新增功能。
  若采用临时输出，需另定生命周期与错误处理，不作为已交付文件，不产生项目 dirty。

### 编辑与输出的内容契约验证

编辑器的 Markdown 转换与 Rust `pulldown-cmark` 是两套实现，共享的是方言与语义约束，
不是同一个解析器。Word / PDF 使用 Rust 解析链路；人工阅读输出不能替代跨实现测试。

- 新增共享的 Markdown 语义 fixture，由编辑器转换测试与 Rust 中间模型（IR）测试读取。
  对照文字、块类型、嵌套关系、图片引用与图注等语义，不比较 ProseMirror 与 Rust 的内部对象形状。
  沿用 `src-tauri/fixtures/` 作为共享测试资产根目录，具体子目录与用例文件组织在实现时确定。
  预期语义使用中立的 JSON 块树，包含块类型、文字、子节点、图片引用及图注等必要信息；
  TS 与 Rust 各自在测试侧将内部结构投影到此格式再比较，具体 schema 在实现时确定，
  不将测试格式引入 Domain、产品协议或运行时转换链路。
- `src/ui/editor/markdown.test.ts` 负责解析 / 序列化往返与 fixture 语义；
  Rust `render::markdown` 测试负责原始 Markdown 及编辑器序列化后的 Markdown 均得到预期 IR。
  采用提交入库的 golden 文件连接两端，无需在每次测试时启动另一种语言的测试进程：
  - 每个共享用例包含原始 Markdown、编辑器生成的 `.serialized.md` 与预期语义数据。
  - Vitest 执行 `serialize(parse(input))`，通过 `await expect(output).toMatchFileSnapshot(path)`
    对照 `.serialized.md`，同时验证预期语义与往返行为。字符串输出直接作为文件内容。
  - 使用 Vitest 自带 `-u` 显式更新 golden，只写入编辑器实际输出，不手工编写 `.serialized.md`，
    不增加自定义更新开关或脚本。更新时审查 diff，不自动更新预期语义以迎合实现。
  - 项目要求默认测试运行只读；实现时使用 Vitest 的 `update: 'none'` 默认配置或等效选项，
    缺失 golden 也须失败。Vitest 本机原生默认会生成缺失快照，不能仅靠“不传 -u”保证只读。
    `-u` 显式覆盖默认更新模式。见 [Vitest 文件快照](https://vitest.dev/guide/snapshot#file-snapshots)
    与 [更新模式](https://vitest.dev/config/update)。本约束不假设项目已有 CI。
  - Rust 分别解析原始输入与 `.serialized.md`，断言其 IR 符合预期语义。
    已知规范化差异须在 fixture 中明确，不能把允许的语义差异当成全面跳过验证的理由。
  - 编辑器输出变化先使 TS 测试失败；重新生成并审查 golden 后，必须再运行 TS 与 Rust 两侧测试。
    golden 及其更新流程是测试资产，不参与产品运行时，不引入自定义 Vue SFC 加载器。
- 覆盖独立图片 / 行内图片及图注判断、表格、列表、正文标题、中文强调边界、原始 HTML、换行与嵌套；
  已知 Markdown 表达限制单独声明，不要求内部表示或 Markdown 字节一致。
- 实施（已完成）：用例在 `src-tauri/fixtures/markdown/`，每个用例 `<name>.md`（原文）、`<name>.json`
  （人工审查的预期语义，可带 `说明` 字段声明已知限制）、`<name>.serialized.md`（golden）。
  测试位于 `src/ui/editor/markdown_contract.test.ts`（与 `markdown.test.ts` 同属编辑器转换测试）
  和 Rust `render::contract_tests`（`render::markdown` IR 的契约测试）；`vite.config.js` 设 `update: "none"`。
  语义格式：块为 `{type: paragraph|heading|figure|quote|code|rule|list|table, …}`，列表项为
  `{task: null|true|false, blocks}`；行内为文字 / 行内代码 / 图片片段加排序后的标记集合
  （`strong`、`emphasis`、`strike`、`link:<url>`），相邻同标记文字合并，硬换行为 `{break: true}`。
  两端各自在测试侧投影：Rust 的软换行记为空格、任务标记（☐ / ☑）记为 `task`、同种强调的嵌套视为同一标记。
- `buildRenderRequest` 的 Application 测试负责章节顺序、标题层级与自动编号；
  Word / PDF 的输出测试负责把共享 IR 正确转成各自输出。移除 HTML 预览不取消这些验证责任。

### PDF 配置与项目会话

- 引入 PDF 配置时，Application 项目会话持有文档与 PDF 配置两部分项目状态；
  `WriterDocument` 继续只表达内容与结构，不把 PDF 配置塞回正文领域模型。
- 修改 PDF 配置属于项目修改，应推进项目 revision、产生项目 dirty，并使用现有自动保存、
  保存串行化与关闭保护。编辑环境主题仍不属于项目状态。
- 保存快照包含同一时刻的文档与 PDF 配置，只有该快照提交成功才推进 savedRevision；
  保存期间的新正文或配置修改仍为 dirty。只改配置不应重写未修改的正文文件。
- PDF 配置不进入正文撤销历史；是否提供独立的配置撤销暂未确定，须在配置功能实施前确认，
  本次旧样式移除不引入新的撤销系统。
- PDF 生成使用同一次操作捕获的内容与配置快照；具体类型名和持久化字段待配置功能设计时确定。

### 旧样式移除与旧项目处理（已完成）

旧实现中的 `DocumentTheme` 曾同时作用于编辑器、Word 与 PDF，`writer.json.style` 保存主题、全局调整与
图片文件级的尺寸 / 对齐覆盖，图片布局以装饰呈现并作为不改变正文的 step 参与撤销。这些已全部移除：

- 文档模型与项目格式中没有 `DocumentStyle` / `WriterDocument.style` / `writer.json.style`
  （含 `theme`、`overrides`、`images`），没有迁移到另一套文档样式或局部布局数据中。
- 旧项目的 `style` 整体忽略，不参与文档组装、编辑展示或导出；打开时不写盘，正常保存时不再写出。
  正文、图片引用、图注和资源文件保留。具体磁盘规则见 `docs/project-format.md` 第 3.1 节。
- 编辑环境使用自己的默认展示参数（`ui/editor/editor_theme.ts`），不从旧项目样式推导；
  可调整项与应用偏好的保存另行设计。
- Application 会话中没有样式修改用例；编辑器中没有单张图片的布局入口、同步状态与布局撤销。
  图片的插入、选择、删除与正文撤销保留。
- 导出请求（`RenderRequest`）只有标题与章节内容 / 结构；Word 与 PDF 各自取得默认输出参数（`export::theme`）。
- PDF 文档级排版配置独立设计，不复用旧 `style`。具体字段、存储结构和默认值尚未确定，实施前更新相应格式契约。
