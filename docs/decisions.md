# 产品与技术决策

已确定、需要长期保持的决策。修改任何一条前，先与产品负责人确认并更新本文件。

## 1. 正文文件名

正文文件名由章节编号决定（`content/ch_2_1.md`），ChapterId 是稳定内部身份。
编号变化时文件必须重命名，一致性由 persistence 层的保存事务保证。
详见 `docs/project-format.md` 第 2、5 节。**不得改用 ChapterId 作为文件名。**

## 2. 编辑器

- 用户编辑的是结构化正文，而不是 Markdown 源码。不以"源码编辑器"为产品方向，也不要求用户理解 Markdown。
  （早期 MVP 使用 CodeMirror 6 做 Markdown 源码编辑，已整体迁移到 ProseMirror，不保留源码编辑模式。）
- ProseMirror 是正文编辑器的内部文档模型和交互内核；schema（`ui/editor/schema.ts`）是正文结构的权威定义。
- 后续正文编辑能力优先基于 ProseMirror schema / command / plugin 扩展，而不是通过 Markdown 文本操作实现。
- Markdown 继续作为正文的持久化格式；领域模型（正文是 Markdown 字符串）、正文磁盘格式及 Rust 导出内容解析保持不变。
  Markdown ⇄ ProseMirror 文档的转换只发生在编辑器层（`ui/editor/markdown.ts`）。
- Markdown 方言与导出的 pulldown-cmark 一致：CommonMark + GFM 表格、删除线、任务列表、脚注（第 11 节）、公式（第 14 节）；原始 HTML 与 Markdown 标题视为文字
  （见第 8 节“正文不支持标题与 HTML”）。
- schema 只包含 Markdown 能保存、且 Rust 渲染器能渲染的结构；不能用 Markdown 保存的能力（合并单元格、
  单元格内多段落、列宽等）不进入编辑器。需要新增此类能力时，先与产品负责人确认是否调整持久化格式。
- 提供常用操作入口：图片、表格、列表、粗体、斜体、引用、代码块；另有 Markdown 风格的输入规则作为快捷输入。
- 编辑器不得对未编辑的正文做任何规范化；只有用户真正修改的章节才会被写回（编辑后又撤销回原样时写回原文）。
  被修改的章节按统一风格整体重新写出，渲染结果不变；CRLF、BOM、结尾是否换行保持原文件的风格。

## 3. 章节标题与正文

- 章节标题只存在于文档结构（manifest）中，Markdown 正文不重复保存章节标题。
- 章节编号不存入正文，也不存入 ChapterNode；编号永远由树结构推导（`chapter_numbering`）。
- 编辑展示和导出时根据章节树深度和编号生成章节标题。

## 4. 保存

- 自动保存（防抖）+ Cmd/Ctrl+S 手动保存。
- **dirty 状态的边界**：只有当存储层明确返回"本次保存已提交"时，才把
  "发起保存时的那份快照"标记为已保存。
  - 保存失败（无论在提交点前还是后）→ 文档保持 dirty，错误对用户可见，之后会重试。
  - 保存进行中用户继续编辑 → 保存成功后文档仍为 dirty（新编辑不属于那份快照）。
  - 同一时间最多一个保存在进行；期间的保存请求合并为之后的一次保存。
- 关闭窗口时若仍为 dirty，先尝试保存；保存失败必须让用户选择，不能静默丢弃。

## 5. 导出

- **能力边界：Writer 负责组织和编辑结构化文档与内容，并生成整洁、可靠的交付文档；不负责后续的精细排版。**
- Word 用于交给他人继续编辑：优先保证内容完整、结构清楚、段落样式规范、便于后续修改，
  不承诺不同 Word / WPS 环境中的折行、分页完全一致。需要精细排版时，导出 Word 后在其他工具中处理。
- Word 的正文、标题与图注使用对应的内置样式（如 Normal、Body Text、List Paragraph、Heading1–9、Caption），
  标题带正确的大纲层级，使接收者能统一修改样式、使用导航窗格与生成目录；不以逐段直接格式代替这些语义样式。
- Word 默认样式向 PDF 默认样式（`docs/pdf-layout.md` 第 3 节）看齐，共用同一套默认输出参数，2026-10-01 确认：
  有文档信息时第一页为封面（标题约在 1/3 高处，下接细线、副标题、作者；不显示页眉页码，正文从第 1 页编号）；
  一级章节另起一页（Heading 1 样式的"段前分页"）；正文段落两端对齐、首行缩进 2 字符、段间不留空；
  页眉为文档标题加细线，页脚居中页码（内置 header / footer 样式）；三线表；引用左侧浅灰竖线；分隔线为居中短线。
  不提供 Word 配置、预览，也不读取 PDF 排版配置。页眉中的当前章节名依赖 Word 域的更新，不生成。
  目录（2026-10-03 实施，待产品负责人确认）：封面之后单独一页“目录”，是由标题样式生成的 Word 目录域（两级，与 PDF 默认相同），
  生成时预先填入各级标题文字，域标记为需要更新，Word 打开时询问是否更新以得到页码（WPS 等可能需要手动更新域）。
- PDF 用于直接阅读、打印和正式交付：Writer 负责自动排版的页面质量，保证内容可读、无溢出或遮挡，
  接受合理留白，不保证每一页满足特定构图要求。
- 编辑展示、Word 输出与 PDF 排版职责独立：内容与结构必须一致，不要求字体、版心、折行、分页或图片显示尺寸一致。
- Word / PDF 导出随 Writer 自带，**不依赖用户安装 Pandoc 或 LibreOffice**。
- Word：Rust `docx-rs` 生成。
- PDF：优先内嵌 Typst（实现方案，不是产品约束）。若发现明显的跨平台、体积或字体问题，
  先与产品负责人沟通再调整。
- Word 与 PDF 共用同一个 Markdown 解析器及内容中间模型（Rust `pulldown-cmark`）；
  编辑器使用自己的 Markdown 转换实现，内容与结构一致性由跨实现契约测试保证。

## 6. 字体

- 字体按"字体族"配置：衬线（宋体类）、无衬线（黑体类）、楷体、等宽；每个字体族是一个有序的候选字体列表（fallback 链），
  同时包含拉丁字体与中文字体，覆盖 macOS / Windows / Linux 的常见字体。Word 默认样式与 PDF 文档级排版
  为正文、标题、图注等元素选择衬线或无衬线；引用固定使用楷体（西文沿用衬线，本机没有楷体时退回宋体，
  不随正文字体配置变化，2026-10-01 确认）；等宽用于代码。编辑展示默认可复用这些候选，
  但不受输出字体族范围约束。
- 选择字体时按列表顺序使用第一个可用的字体，逐字形回退。
- 预留"随应用打包字体"的位置：打包字体始终参与查找，未来可放入开源中文字体保证一致性。
- 找不到任何可显示中文的字体时，导出给出明确警告，而不是静默输出缺字。
- 输出字体候选配置集中在一处（Rust `export::fonts`），不在各导出器里各写一份。
  编辑展示使用自己按屏幕阅读挑选的字体栈（`ui/editor/editor_theme.ts`），不与输出字体候选绑定。
- PDF 排版设置中的字体选择限于可可靠输出的受控字体族，不提供任意系统字体列表。
- 编辑环境字体不受输出字体族范围限制，可以使用本机字体；是否提供系统字体选择入口另行设计。
  编辑字体不进入项目或输出请求，不因此承诺跨机器一致。
- 打包字体：把 .ttf / .otf / .ttc 放入应用资源目录下的 `fonts/`（Tauri `bundle.resources`）即参与 PDF 排版的字体查找；
  要让它成为首选，把它的字体族名加到 `export::fonts::families` 对应字体族列表的前面。
  已打包（2026-10-03 实施，待产品负责人确认）：Noto Serif CJK SC 与 Noto Sans CJK SC 的常规与粗体（SIL OFL 1.1），
  排在衬线 / 无衬线中文候选的最前面，各平台 PDF 的中文字形与折行一致（拉丁字体仍按原候选）。
  字体约 80 MB，不提交到仓库：构建正式包前 `scripts/fetch-fonts.mjs` 下载并校验（beforeBuildCommand），
  开发环境没有下载时按本机字体回退。楷体与等宽不打包。
  Word 只写字体名，由用户机器上的 Word 负责替换。

## 7. 稳定性

- release 构建使用 `panic = "unwind"`：第三方排版库（Typst、docx-rs）遇到异常输入时 panic 只让本次导出失败，
  不会让整个应用退出。导出在后台线程执行，panic 被转换为普通错误返回给界面。
- 来自用户项目的数据（图片、正文）中的任何问题都不能让应用崩溃：图片解码带尺寸 / 内存上限，
  失败时以占位文字输出并在导出报告中列出。

## 8. 内容与排版分离（编辑展示与自动排版）

- **Markdown 是正文内容的持久化格式，不承担完整排版语言的职责。** 正文只表达"这是什么"（段落、列表、引用、
  代码、表格、图片、图注等），由 Markdown + ProseMirror schema 表达。
- **正文不支持标题与 HTML。** 文档结构只由章节树表达，章节标题与编号由结构生成；正文中没有标题节点，
  也没有输入、菜单或导出中的正文标题。已有正文中的 Markdown 标题（`# …`、Setext 标题）当作普通段落，
  文字是标题的原文（如“## 研究背景”），其中的强调等记号也只是文字，编辑后写回时转义（`\## 研究背景`）；
  块的边界仍按 Markdown 标题判断。原始 HTML 同样一律是文字。编辑器与 Rust 导出按同一规则处理，由共享 fixture 约束。
- **编辑阶段只关注内容**：提供默认美观、易读的展示，不提供输出排版设置入口，不以最终页面效果为编辑目标。
  粗体、斜体、列表等正文表达能力继续保留。
- **“主题”指编辑环境主题，属于应用级偏好**：用于调整编辑环境的视觉与阅读体验，不是文档样式，
  不随项目保存，不改变正文、不产生文档 dirty 状态，也不影响 Word / PDF 输出。
  具体可调整项在后续设计时确定；开发版与正式版的主题偏好遵循应用状态隔离规则。
  目前已有外观（“显示 → 外观”：跟随系统 / 浅色 / 深色，默认跟随系统），整个应用（窗口、系统菜单与对话框、
  界面与正文配色）一起切换；配色在 `ui/tokens.css`。
- **解除一份主题同时控制编辑界面、Word 与 PDF 的绑定**。Word 提供规范的默认输出样式；
  PDF 在排版阶段提供少量文档级配置，称为排版配置，不复用编辑环境主题的概念。
  默认样式、配置项与默认值见 `docs/pdf-layout.md`。
- **PDF 采用规则驱动的自动排版**：文档级配置随项目保存并复用，排版始终基于当前正文，
  不维护另一份可独立编辑的内容。内容变化后重新计算页面，正式交付前检查更新后的结果。
- **不提供针对特定内容元素的手工排版或局部布局覆盖**：包括单张图片尺寸 / 对齐 / 独占一页、
  单个段落间距、手工分页、固定页码位置和页面坐标调整。图片、图注、表格等按统一规则自动安排。
  不为这些排版设置引入元素实例身份。未来扩展此边界须先与产品负责人确认。
- **图片大小、对齐、位置等展示 / 布局信息不属于文档内容或文档元数据**，不为单张图片保存这些设置，
  也不转移到 Markdown、资源文件 metadata 或另一份局部布局配置中。
  编辑展示按统一规则适应编辑区，Word / PDF 按各自的统一排版规则适应输出区域；图片引用与图注仍属于内容。
- 标题跟随正文、图片与图注保持在一起、图片适应页面、跨页表头重复等由排版引擎处理。
  不理想的页面优先通过改善通用规则解决，不要求用户逐页维护；最终输出需可检查，
  通过导出 PDF 后在外部阅读器中检查，不提供应用内的全文分页预览。
  例外：PDF 排版设置中显示用相同排版生成的文档开头样张，用于判断设置效果（2026-10-01 确认，见 `docs/pdf-layout.md` 第 5 节）。
- **不因为新增视觉能力默认扩展 Markdown 方言**（例如 `{width=60%}`、`<span style>`）。如果未来某项核心文档语义
  无法由 Markdown 表达，由产品负责人决定是否扩展 Markdown 或改变存储模型。
- 排版配置随正常的项目保存事务提交，不引入第二套保存流程，不进入正文或正文撤销历史。
  排版使用语义参数（字体族、磅值、倍数等），Rust 不理解前端 CSS。

### 图片自动尺寸约束

- 保持宽高比，统一规则下小图不放大，宽图缩到可用宽度，竖长图同时受可用高度限制。
- 独立图片按完整页面正文区域的可用宽、高计算尺寸上限；有图注时为图注及必要间距预留空间。
  尺寸与图片落在页上的位置无关，不按当前页剩余空间缩小图片。
- PDF 当前页空间不足时将图片与图注整组移到下一页，不为塞进页底压缩图片；
  仅当完整页面的正文区域或图注占用空间改变时重新计算尺寸，不挤占页眉页脚或裁掉内容。
- Word 按写入的纸张、页边距及图注空间计算尺寸上限，并表达图片与图注保持在一起的约束；
  实际分页由 Word / WPS 完成，Writer 不依据其运行时剩余页面空间调整图片尺寸。
- 行内图片受所在容器的可用宽度限制（例如表格单元格），同时保持比例、不放大，
  在分页输出中仍受完整正文区高度上限限制；不默认按文字行高压成小图。
  表格单元格的可用宽度按列数等分正文宽度、再减去单元格左右内边距（Word 使用默认的 108 twip，
  PDF 使用 6pt）。PDF 中没有图片的表格列宽仍随内容；含图片的表格各列等宽（与 Word 相同），
  表头高度按与最终表格相同的列宽、在表格实际所在容器的宽度下测量。
  列表与引用中的图片同样受缩进后的可用宽度限制。
  表格中含图片的行不能跨页拆开，而表头在每页重复：正文行中的图片高度不超过正文区减去表头高度与
  单元格上下间距；表头中的图片不超过正文区高度的四分之一，避免重复的表头占满页面。
- 预留空间的计算：PDF 在排版时实际测量图注与表头的高度（按实际字体、宽度与折行），不做估算；
  Word 的排版结果无法在导出时测量，按折行上限保守估计（每个字符按 1em、按单词贪心折行），
  预留偏大只会让图片略小，不会让图注或图片被挤出正文区。
  不设最小显示宽度：极窄的长图宽度可以小于 1pt，高度上限优先。
- 图片固有物理尺寸如何解释 DPI、缺少 / 异常 DPI 时的回退值仍待确定；
  实施统一尺寸算法前须明确该策略，并覆盖高分辨率截图、无 DPI、小图与竖长图用例。
  不以图像元数据直接覆盖页面边界限制，也不把 DPI 转成单图布局设置。
- 待评估的 DPI 方案：PNG / JPEG 元数据在 72–600 DPI 范围内时按其换算，缺失或异常时按 96 DPI。
  这是候选方案，不作为已确认算法；实现前检查横纵 DPI 不一致、解码后元数据保留和跨格式行为。
- 当前实现（`export::images`、`export::pdf`、`export::docx`）：页面边界、图注与表头预留、容器宽度与"不放大"规则已落实；
  图片固有尺寸仍按移除旧样式前的固定 96 DPI 换算，不读取图像元数据。DPI 策略确定后只需替换这一换算。

### 移除预览（已完成）

- 移除应用内全文 HTML 预览，不新增应用内 PDF 分页预览；取消预览按钮、菜单、工作区模式切换、
  预览章节点击选择与滚动同步、预览刷新状态和相关偏好。章节树与单章编辑继续承担内容导航。
- 连续阅读由之后的“全文阅读”重新提供（见下节），它属于编辑环境，不是 HTML 预览的恢复。
  最终页面检查仍通过导出文件在外部阅读器中进行。
- 移除 `DocumentPreview.vue`、预览 composable、Application / Infrastructure 的预览端口与调用、
  Rust `render_preview` command 和仅供预览使用的 HTML 渲染模块及相关测试 / Story。
  保留 Word / PDF 使用的 Markdown 解析、IR、章节请求组装与资源安全解析，避免随预览一并删除。
- `RenderRequest` 移除 `theme`、`images`，只携带文档标题及按阅读顺序展开的章节内容与结构；
  Word / PDF 各自取得默认输出参数，未来 PDF 配置独立传入，不恢复共享主题。
- 之前“HTML 预览暂用编辑默认参数”的过渡规则取消，移除预览不以新主题或 PDF 配置为前置条件。
  未来重新引入任何应用内预览需单独确认产品需求（PDF 排版设置中的样张已于 2026-10-01 确认）。
- 外部阅读器检查的操作成本需要评估；候选方式包括导出成功后“打开文件”，
  或按需生成到临时目录并用系统阅读器打开。两者均未确定，不随预览移除新增功能。
  若采用临时输出，需另定生命周期与错误处理，不作为已交付文件，不产生项目 dirty。

### 全文阅读（已确认，2026-09-30）

产品需求：快速滚动浏览整篇文档。按内容与排版分离的边界，它是编辑环境的只读展示，不是导出效果预览。

- 连续显示所有章节的编号、标题与正文（阅读顺序与导出相同），没有分页，不承诺与 Word / PDF 的页面一致，
  也不承担最终页面检查。
- 前端渲染：与编辑器使用同一套 Markdown 解析、schema、编辑环境主题与正文样式
  （`ui/editor/document_body.css`），看到的正文与编辑时完全相同。不恢复 Rust HTML 渲染、
  `render_preview` command 或输出端口。
- 只读：不产生修改、不进入撤销历史、不产生 dirty。编辑器在阅读期间保持挂载，各章节的撤销历史不丢失。
- 与章节树双向联动：滚动时视口顶端所在的章节成为当前章节；在章节树中选择章节时滚动到该章节开头。
  进入与离开阅读时按块对齐位置（同版心、同样式，块高度相同），眼前的文字停在原处；
  回到编辑时光标放在视口中第一个完整显示的块的开头。
- 入口：工具栏“全文阅读”开关、“显示 → 全文阅读”（阅读中打勾）与 ⇧⌘R（Safari 阅读器的按键）。
  Esc / Enter 或再次触发回到编辑；章节树中 Enter 回到编辑该章节；⌘J 在章节树与阅读区之间切换。
- 阅读状态不持久化，不属于应用偏好。

### 编辑与输出的内容契约验证

编辑器的 Markdown 转换与 Rust `pulldown-cmark` 是两套实现，共享的是方言与语义约束，
不是同一个解析器。Word / PDF 使用 Rust 解析链路；人工阅读输出不能替代跨实现测试。

- 新增共享的 Markdown 语义 fixture，由编辑器转换测试与 Rust 中间模型（IR）测试读取。
  对照文字、块类型、嵌套关系、图片引用与图注等语义，不比较 ProseMirror 与 Rust 的内部对象形状。
  沿用 `src-tauri/fixtures/` 作为共享测试资产根目录，具体子目录与用例文件组织在实现时确定。
  预期语义使用中立的 JSON 块树，包含块类型、文字、子节点、图片引用及图注等必要信息；
  TS 与 Rust 各自在测试侧将内部结构投影到此格式再比较，具体 schema 在实现时确定，
  不将测试格式引入 Domain、产品协议或运行时转换链路。
- `src/ui/editor/markdown.test.ts` 负责解析 / 序列化往返与 fixture 语义；
  Rust `render::markdown` 测试负责原始 Markdown 及编辑器序列化后的 Markdown 均得到预期 IR。
  采用提交入库的 golden 文件连接两端，无需在每次测试时启动另一种语言的测试进程：
  - 每个共享用例包含原始 Markdown、编辑器生成的 `.serialized.md` 与预期语义数据。
  - Vitest 执行 `serialize(parse(input))`，通过 `await expect(output).toMatchFileSnapshot(path)`
    对照 `.serialized.md`，同时验证预期语义与往返行为。字符串输出直接作为文件内容。
  - 使用 Vitest 自带 `-u` 显式更新 golden，只写入编辑器实际输出，不手工编写 `.serialized.md`，
    不增加自定义更新开关或脚本。更新时审查 diff，不自动更新预期语义以迎合实现。
  - 项目要求默认测试运行只读；实现时使用 Vitest 的 `update: 'none'` 默认配置或等效选项，
    缺失 golden 也须失败。Vitest 本机原生默认会生成缺失快照，不能仅靠“不传 -u”保证只读。
    `-u` 显式覆盖默认更新模式。见 [Vitest 文件快照](https://vitest.dev/guide/snapshot#file-snapshots)
    与 [更新模式](https://vitest.dev/config/update)。本约束不假设项目已有 CI。
  - Rust 分别解析原始输入与 `.serialized.md`，断言其 IR 符合预期语义。
    已知规范化差异须在 fixture 中明确，不能把允许的语义差异当成全面跳过验证的理由。
  - 编辑器输出变化先使 TS 测试失败；重新生成并审查 golden 后，必须再运行 TS 与 Rust 两侧测试。
    golden 及其更新流程是测试资产，不参与产品运行时，不引入自定义 Vue SFC 加载器。
- 覆盖独立图片 / 行内图片及图注判断、表格、列表、Markdown 标题（作为文字）、中文强调边界、原始 HTML、换行与嵌套；
  已知 Markdown 表达限制单独声明，不要求内部表示或 Markdown 字节一致。
- 实施（已完成）：用例在 `src-tauri/fixtures/markdown/`，每个用例 `<name>.md`（原文）、`<name>.json`
  （人工审查的预期语义，可带 `说明` 字段声明已知限制）、`<name>.serialized.md`（golden）。
  测试位于 `src/ui/editor/markdown_contract.test.ts`（与 `markdown.test.ts` 同属编辑器转换测试）
  和 Rust `render::contract_tests`（`render::markdown` IR 的契约测试）；`vite.config.js` 设 `update: "none"`。
  语义格式：块为 `{type: paragraph|heading|figure|quote|code|rule|list|table, …}`，列表项为
  `{task: null|true|false, blocks}`；行内为文字 / 行内代码 / 图片片段加排序后的标记集合
  （`strong`、`emphasis`、`strike`、`link:<url>`），相邻同标记文字合并，硬换行为 `{break: true}`；
  章节引用为 `{ref: {id, show} | null, cached}`（地址格式错误时 `ref` 为 null，可带标记）。
  两端各自在测试侧投影：Rust 的软换行记为空格、任务标记（☐ / ☑）记为 `task`、同种强调的嵌套视为同一标记。
- `buildRenderRequest` 的 Application 测试负责章节顺序、标题层级与自动编号；
  Word / PDF 的输出测试负责把共享 IR 正确转成各自输出。移除 HTML 预览不取消这些验证责任。

- PDF 生成使用同一次操作捕获的内容与配置快照；类型与持久化字段见 `docs/pdf-layout.md` 第 5 节、
  `docs/project-format.md` 第 3.2 节。

## 9. 章节交叉引用（已确认方向，2026-10-02；细节待实施时补充）

产品需求：正文中引用其他章节，引用文字随章节结构自动更新，并可跳转。
图与表的编号和引用见第 12 节；段落等其他元素不能被引用。

做法参照 Word 交叉引用、LaTeX `\ref`、DocBook `xref`：引用保存“目标 + 显示格式”，文字在展示与输出时生成。

- **身份**：引用目标是 `ChapterId`，不使用正文文件名（随编号变化）或标题（可重名、可修改）。
  ChapterId 由此进入正文，必须是永久身份：任何操作不得为已有章节重新生成 id。
- **持久化**：使用标准 Markdown 链接语法，只有地址是 Writer 的约定（`writer:chapter/<id>`，格式见
  `docs/project-format.md` 第 4.1 节）。不扩展 Markdown 语法，`version` 不变。
  接受的代价：在其他 Markdown 工具中引用是不可跳转的文字；正文离开 Writer 后失去引用能力；
  旧版 Writer 将其视为普通链接，编辑时原样保留地址，导出时只输出文字。
- **链接文字是缓存**：Writer 读取时忽略，按当前结构生成；只在该章节被编辑写回、或用户执行“更新交叉引用”时
  刷新为当时的生成结果，未编辑的正文不因结构变化而自动改写。外部工具中看到的可能是旧编号，在外部修改这段文字不起作用。
- **显示格式**：编号 + 标题（默认，如“2.1 研究方法”）、仅编号（“2.1”）、仅标题（“研究方法”）。
  引用只生成编号 / 标题，“见……”等连接词由用户书写。
- **编号写法跟随输出**：引用中的编号与目标标题在同一份输出中的写法一致。编辑展示、全文阅读与 Word 使用 `2.1`；
  PDF 跟随排版配置的章节编号样式（“第 2 章”）；编号不显示时，各格式都退回为只显示标题。
- **编辑器**：引用是不可分割的行内节点（整体选中、删除，可带粗体等强调，不能再被普通链接包裹），
  不是 `link` mark。章节改名、移动后，编辑器与全文阅读中的引用文字立即更新，但不改变正文、
  不产生 dirty、不进入撤销历史。
- **失效引用**：目标章节不存在或地址格式错误时，编辑器与全文阅读中以醒目的失效样式显示；
  Word / PDF 输出为文字并列入导出报告，不让打开或导出失败。地址来自可能被外部修改的正文，属于信任边界。
- **导出**：Word / PDF 写入生成好的静态文字，并链接到目标章节标题（PDF 使用标签，
  Word 使用标题上的书签加内部超链接），不使用 Word 域，不提供页码引用。
- **插入**：“插入 → 章节引用…”（⌘K，macOS 惯例的“添加链接”，将来外部链接并入同一面板）与正文右键菜单；
  工具栏不加入口。选中文字时插入的引用替换选中内容。在光标下方弹出选择浮层：
  - 按章节树顺序与缩进列出全部章节（含当前章节），编号弱于标题；按标题或编号搜索，无结果时说明。
  - ↑ / ↓ 选择，Enter 插入，Esc 取消，关闭后焦点回到原光标处。
  - 底部用分段控件选择显示格式，默认“编号 + 标题”；记住本次运行中上次的选择，不持久化。
- **正文中的样子**：与正文同字体、使用链接颜色，不加底色或胶囊；单击整体选中。
  失效引用显示 Markdown 中的缓存文字（提示原来的目标），以警示色与虚线下划线区分。
- **操作已有引用**：右键菜单提供“前往 <编号 标题>”“显示格式”（当前格式打勾）“更改目标…”（⌘K 同样可用）；
  ⌘ + 单击直接前往；悬停提示目标与“⌘ 单击前往”。不在光标经过引用时弹出浮层，避免打扰写作。
- **跳转**：前往时在章节树中选中目标章节、打开其正文、光标置于开头；全文阅读中单击引用直接跳转。
  返回：跳转后以 Toast 提供“返回”，并在“显示 → 返回上一位置”（⌘[）提供固定入口；
  返回后可以“显示 → 前进到下一位置”（⌘]），重新前往别处时清空可前进的位置（与浏览器相同）。
  ⌘[ / ⌘] 因此不再用于列表缩进，列表缩进用 Tab / Shift+Tab 与格式菜单（2026-10-02 产品负责人确认）。
- **删除章节**：被引用的章节在删除确认中说明有多少处引用将失效。
- **更新交叉引用**（兜底，参照 Word“更新域”）：“插入”菜单中“章节引用…”之后（分隔线隔开），不设快捷键。一次性操作，同时完成：
  - 同步：缓存文字与当前生成结果不一致的章节标记为需要写回，由正常保存事务提交；
    这些章节按统一风格整体重新写出（渲染结果不变，其中引用以外的 Markdown 写法也可能被规范化，已接受）。
  - 校验：列出全部失效引用（所在章节与上下文），可跳转到所在位置。
  - 结果在对话框中反馈：首行是结论（更新的章节与引用数量，或“所有引用都是最新的”），
    其下为失效引用列表，点击跳到所在位置并关闭对话框。
  - 不改变编辑器中的内容，因此不进入撤销历史；有章节需要写回时产生 dirty。
- **契约**：Rust 内容中间模型区分章节引用与外部链接；共享 Markdown fixture 覆盖有效、失效与格式错误的引用。

第二期：从章节树拖入正文插入引用（需与章节树拖动排序共存）。

待定：反向引用列表、复制到其他项目时的处理。

## 10. 检查更新（直接分发，2026-10-03 实施，待产品负责人确认）

- 直接分发的安装包使用 Tauri updater：更新包带签名，应用用内置的公钥校验后才安装。
  入口是“帮助 → 检查更新…”；启动约 5 秒后在后台静默检查一次，只有发现新版本时才提示（带“查看”），
  失败与已是最新都不打扰。安装后需要重新启动，重新启动前与关闭窗口相同，先保存并释放打开的项目。
- 更新地址与公钥在**构建正式包时**由环境变量提供（`WRITER_UPDATE_ENDPOINT`、`WRITER_UPDATE_PUBKEY`，见 `src-tauri/src/updater.rs`），
  不写入仓库；没有提供的构建（开发版、自行编译）不检查更新，对话框说明“此版本不检查更新”。
- 发布流程：
  1. 只需一次：`npx tauri signer generate -w ~/.tauri/writer-updater.key` 生成密钥（私钥妥善保管，丢失后已安装的版本无法再更新）。
  2. 构建：`WRITER_UPDATE_ENDPOINT=<latest.json 的地址> WRITER_UPDATE_PUBKEY="$(cat ~/.tauri/writer-updater.key.pub)"
     TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/writer-updater.key)" npm run tauri build -- --config '{"bundle":{"createUpdaterArtifacts":true}}'`。
  3. 上传安装包、`.sig` 与 Tauri 格式的 `latest.json`（`version`、`notes`、`pub_date`、各平台的 `url` 与 `signature`）。
- Mac App Store 版本不得包含自更新（构建时不提供上述环境变量即可，入口显示“此版本不检查更新”；上架前再决定是否隐藏入口）。

## 11. 脚注（2026-10-03 实施，待产品负责人确认）

- 持久化使用 GFM 脚注语法：正文中 `[^1]`，章节末尾 `[^1]: 内容`。不扩展 Markdown，`version` 不变；
  其他 Markdown 工具（GitHub、Typora 等）能直接显示。行内写法 `^[…]` 与没有定义的 `[^x]` 是文字（pulldown-cmark 不支持前者）。
- 编辑器中脚注是行内的原子节点，显示为上标编号（按章节中的顺序），章节末尾在短线下列出全部脚注；全文阅读相同。
  脚注内容只有一段文字（不带格式）：载入时带格式或多行的定义原样保留，内容没有修改就原样写回，修改后按文字写出。
- 插入：“插入 → 脚注…”与正文右键菜单（无快捷键，与 Pages 相同）；先在光标下方的浮层中填写内容，Enter 完成后才插入，
  Esc 取消不留下空脚注。编辑：双击编号、单击章末列表中的一条、选中后按 Enter 或右键“编辑脚注…”；清空内容即删除。
- 写出时引用按章节中的顺序重新编号为 `[^1]`、`[^2]`……，定义写在章节末尾（每条之间空一行）；同一定义被引用多次时，
  每处各是一条脚注（编辑与输出一致）。只有被编辑的章节会这样写出。
- 输出：Word 使用真正的脚注（页底、自动编号，FootnoteText / FootnoteReference 样式）；PDF 使用 Typst 的 footnote。
  两者都在全文中连续编号，编辑展示中的编号只在章节内，这是已接受的差异。
- 契约：共享 fixture `footnotes`，语义投影为 `{footnote: 内容的纯文字}`。

## 12. 图表编号与引用（2026-10-03 实施，待产品负责人确认）

- **编号对象**：有图注的独立图片是“图”，有标题的表格是“表”；没有图注 / 标题的不编号，也不能被引用。
  按一级章节分组、按阅读顺序编号：“图 2-1”“表 3-2”（一级章节号-章内序号）。编辑展示、全文阅读、Word 与 PDF 相同
  （PDF 的章节编号样式为“第 2 章”或不显示编号时仍写作“图 2-1”）。
- **输出**：图注前加编号（“图 2-1　研究流程”，全角空格分隔）；表格标题在表格上方（Caption 样式 / 图注样式，与表格留在同一页）。
- **表格标题的持久化**：采用 Pandoc 的写法——紧接在表格之前、原文以 `Table: ` 开头的段落是表格的标题，
  结尾 `{#tbl:<id>}` 是标识。按原文判断：写出普通段落时把段首的 `Table:` 转义为 `Table\:`。
  在其他 Markdown 工具中显示为表格前的一段文字（Pandoc 中是真正的表格标题），已接受。
- **身份**：被引用时才分配标识（8 位小写字母与数字），写在正文中：图写在图片的 title（`![图注](src "fig:<id>")`，
  Pandoc 旧的图片约定），表写在标题结尾。标识只能是字母、数字、- 与 _；引用前没有标识的图表在第一次被引用时写入。
- **引用**：`[图 2-1](writer:figure/<id>)`、`[表 2-1](writer:table/<id>)`，与章节引用共用节点、插入入口（⌘K 浮层中章节之后列出图表，
  选中图表时没有显示格式）、跳转（前往图表所在章节）、失效显示、更新交叉引用与导出报告；链接文字同样是缓存。
  Word 中链接到图注 / 标题上的书签，PDF 中链接到图表的标签。
- 编辑器中：图注前显示编号；表格标题显示在表格上方，单击编辑，右键菜单“添加 / 编辑表格标题…”，清空即去掉标题。
- 契约：共享 fixture `element-refs`（图片标识、表格标题与标识、转义、引用地址），`chapter-refs` 中 `writer:figure/1` 改为图表引用。

## 13. 参考文献与文献引用（2026-10-03 实施，待产品负责人确认）

- **条目属于文档内容**：`WriterDocument.references`，保存在 writer.json 的 `references`（project-format 3.3），随正常保存提交，
  不进入正文撤销历史。类型：专著、期刊文章、书中章节、学位论文、报告、网页、其他；字段按类型显示。
- **著录格式**：GB/T 7714—2015 顺序编码制（`domain/bibliography` 的 `formatReference`）；作者超过 3 位时加“等”/ et al。
  格式在前端生成，随导出请求传给 Rust（Word 与 PDF 共用同一份文字）。暂不提供其他格式（著者-出版年制、APA 等）与 BibTeX 导入。
- **引用**：正文中是地址为 `writer:cite/<条目标识>` 的链接（project-format 4.3），与章节引用共用节点；显示为上标“[编号]”，
  按全文中第一次引用的顺序编号，同一条目再次引用使用同一编号；条目不存在时显示为失效引用并列入导出报告。
  链接文字是缓存，插入时按插入位置计算编号。
- **入口**：“插入 → 文献引用…”（光标下方的浮层：搜索、↑↓、Enter；底部“管理参考文献…”）、正文右键菜单；
  “插入 → 参考文献…”打开对话框（列表 + 表单 + 著录预览；修改在“完成”时一次提交，删除被引用的条目先确认）。无快捷键。
- **输出**：正文之后一个不编号的一级标题“参考文献”，按编号列出被引用的条目（未被引用的不输出）；
  引用是上标的“[编号]”，链接到条目（Word 书签 / PDF 标签）。PDF 目录中包含“参考文献”。
- 契约：共享 fixture `citations`，语义投影为 `{cite: 标识, cached}`。

## 14. 数学公式（2026-10-03 实施，待产品负责人确认）

- **持久化**：`$…$` 行内公式、`$$…$$` 行间公式，内容是 LaTeX（与 GitHub、Typora、pulldown-cmark 的 ENABLE_MATH 相同）。
  只含一个 `$$…$$` 的段落是公式块。规则：开头的 `$` 后与结尾的 `$` 前不是空白，结束的 `$` 与开始的处在同一层花括号中，
  公式中不能有未转义的 `$`。编辑器写出时文字中的 `$` 一律转义（`\$`）。
- 已接受的变化：已有正文中成对的 `$`（如“$5 与 6$”）从此显示为公式；不需要时写成 `\$`。
- **编辑器**：行内公式与公式块是原子节点，用 KaTeX 显示（无法识别的写法以红色原文显示）；
  “插入 → 行内公式… / 公式块…”与右键菜单（无快捷键，与 Pages 相同），先在浮层中填写 LaTeX（下方实时预览），
  Enter 完成，⇧Enter 换行；双击、选中后按 Enter 或右键“编辑公式…”编辑，清空即删除。输入 `$…$` 自动转换为行内公式。
- **输出**：PDF 用 mitex 把 LaTeX 转换为 Typst 公式排版（规格文件 vendored，见 `src-tauri/vendor/mitex-specs/WRITER-PATCH.md`）；
  Word 中每个公式用同样的 Typst 排版渲染为图片嵌入（接收者不能编辑公式，不生成 OMML）。
  转换或排版失败的公式以红色 LaTeX 原文输出，导出提示中说明数量（报告 `invalidFormulas`），导出不失败。
  编辑展示（KaTeX）与输出（Typst）是两套排版，支持的命令范围略有不同。
- 契约：共享 fixture `math`，语义投影为 `{math: tex, display}` 与 `{type: "math", tex}`。

## 15. 专注模式（2026-10-03 实施，待产品负责人确认）
