# 长期风险与结论

本轮评估后决定暂不修改、但需要记录的三项风险。

## 1. 树操作递归，极深文档可能栈溢出（已解决）

> 已处理：Domain 引入 `MAX_CHAPTER_DEPTH = 32`。`validateTree` 超过上限即停止深入并报告
> `depth-exceeded`，移动与插入也不能产生超限的树，因此所有递归遍历的深度都有上界。
> 以下为原始记录。

`chapter_tree`、`chapter_numbering`、拖拽定位与渲染摊平都使用递归遍历。
正常导入的文档深度远达不到引擎调用栈上限，但恶意或异常深的导入数据理论上可能触发
`RangeError: Maximum call stack size exceeded`。

结论：本轮不重写全部树算法。后续接入文件导入时，优先在信任边界上：
- 把 `validateTree` 改成显式栈遍历，或
- 明确并验证一个最大章节深度，超限直接拒绝导入。

## 2. 章节重排只有鼠标拖拽（已解决）

> 已处理：选中章节可以用键盘上移 / 下移 / 提升 / 降级——章节获得焦点时按 Shift+F10（或菜单键）打开章节菜单选择，
> 或使用菜单栏"章节"中的同名命令。Application `keyboardMoveIntent` 把方向换算成与拖拽相同的 `MoveIntent`，
> 仍由 `moveChapterTo` 执行，没有新增移动规则。（早先的 Alt+Shift+方向键 快捷键已取消：Writer 的快捷键只用
> "⌘ + 一个键"，见 `src/ui/common/shortcuts.ts`。）以下为原始记录。

`ChapterTree` 仅实现 HTML5 拖拽，键盘用户无法重排章节。

结论：本轮不实现。做可访问性时，为选中章节增加「上移 / 下移 / 提升 / 降级」快捷键，
复用 Application 的 `moveChapterTo`，不新增移动规则。

## 3. 折叠状态只按章节 ID 保存（已解决）

> 已处理：折叠状态由工作区按项目持有（保存在各项目的 `.writer/ui-state.json`），
> 切换项目时工作区整体重建，不会继承上一份文档的折叠状态。以下为原始记录。

`ChapterTree` 的 `collapsedIds` 只有章节 ID。未来支持多文档时，不同文档里相同的
章节 ID 会继承上一份文档的折叠状态。

结论：本轮只有一个文档来源，不处理。引入多文档后，把折叠状态的键改为
「文档 ID + 章节 ID」，或在切换文档时清空 `collapsedIds`。

## 4. 外部程序修改项目文件（已处理）

Writer 打开项目时把全部正文读入内存。打开期间如果用其他编辑器修改了某章节的 `content/*.md`：
- 该章节在 Writer 中未被编辑 → 换名时按字节保留磁盘上的版本，外部修改不丢；
- 该章节在 Writer 中也被编辑 → Writer 保存时以自己的版本覆盖。

结论（2026-10-03 更新，已处理）：窗口获得焦点时与每 15 秒读取一次磁盘上的项目，与最近一次确认的状态比较：
只在外部修改、Writer 中没有修改的章节直接载入并提示；两边都修改了正文、或章节结构 / 标题 / 文档设置被修改时，
询问保留 Writer 中的版本（保存时覆盖）还是使用磁盘上的版本。不做逐字合并；正在保存时不检查。
多个 Writer 进程仍由项目独占锁（`.writer/lock`）阻止。

## 5. 真实桌面环境的端到端验证

自动化测试覆盖了 Domain / Application / UI（内存存储）与 Rust 存储 / 渲染 / 导出，
但原生对话框、窗口关闭 / 退出流程、Word 中的最终排版需要在真实桌面环境中手动核对。

结论：每次发布前按 `docs/implementation-plan.md` 的"手动验收清单"执行一遍。

## 6. 安装包体积

内嵌 Typst 后 release 可执行文件约 46 MB（gzip 后约 21 MB），其中 Typst 内嵌字体约 9.6 MB。

结论：可接受。若需要缩小，可去掉 `typst-kit` 的 `embedded-fonts`，完全依赖系统拉丁字体。

## 7. 结构化编辑与 Markdown 表达能力

正文以 Markdown 保存，编辑器中的结构必须能写回 Markdown。只有被编辑过的章节会重新写出，此时：

- 强调（粗体 / 斜体 / 删除线）边界紧挨中文标点、外侧紧挨文字时（是**“重要”**的），CommonMark 规则下会变成字面星号。
  写出时把边界上的标点移到标记外（是“**重要**”的）；极少数相邻多重强调仍无法表达时去掉该处格式。文字本身永远不变。
- 未被使用的链接引用定义（`[x]: url`）与没有被引用的脚注定义在渲染结果中本来就不可见，编辑该章节后会被去掉；
  引用式链接改写为行内链接。
- 文字中的 `$` 编辑后写成 `\$`（否则成对的 `$` 会成为公式，decisions 第 14 节）。
- 原始 HTML 在编辑展示 / 导出中显示为文字，编辑后以转义后的文字保存。
- Markdown 标题（包括其他工具写的）在编辑展示 / 导出中是原文文字的段落（如“## 研究背景”），编辑该章节后以转义后的文字保存
  （`\## 研究背景`），在其他 Markdown 工具中也不再是标题。正文不支持标题（decisions 第 8 节）。
- 行首空白、空段落、段首段尾的硬换行在 Markdown 中不显示，写出时去掉；列表的紧凑 / 松散按 Markdown 规则确定。
- 块级嵌套达到 100 层的内容（远超 Rust 渲染器的 32 层）在编辑器中无法完整表示，编辑该章节会丢失超出的部分。

- 同一种强调嵌套在自身之中（CommonMark 解析 `**“甲”**乙**“丙”**` 得到粗体里的粗体）在编辑器中合并为一层，
  显示与导出一致（整段粗体）；编辑后写出为一层的 `**…**`。

结论：以上都是 Markdown 本身的表达限制；内容与结构应在编辑器及导出中一致（由共享语义 fixture 验证），
不承诺页面视觉、折行或分页一致，不为此改变存储格式。

## 8. 编辑展示与输出的限制

- 编辑环境主题不影响 Word / PDF，三种场景不承诺字体、版心、折行、分页或图片尺寸一致。
  验收关注内容与结构完整，以及各自场景的可读性。
- Word 只写字体名，实际字形与分页由打开文档的机器和 Word / WPS 决定。
- PDF 字体选择仍需要可靠的候选字体与回退；系统中文字体差异可能影响排版，
  不打包中文字体（decisions 第 6 节，避免安装包增加约 80 MB），不同机器的 PDF 中文字形与折行可能不同。
- 统一自动排版可能产生合理留白或无法满足特定页面构图。这是已接受的能力边界，
  不通过增加局部布局覆盖或元素实例身份解决；需要精细排版时导出 Word 后处理。
- 内容变化会触发 PDF 重新分页，正式交付前应重新检查当前内容的输出结果。
- 全文阅读只是编辑环境的连续展示，不能代替导出后的页面检查；检查导出文件的操作成本仍待评估，
  “打开文件”或临时生成方案仍是候选。
- 全文阅读打开时一次生成全部章节的 DOM：约 200 万字在 Chrome 中约 0.4 s（Storybook `App/LargeDocument`），
  WKWebView 中尚未实测；图片加载完成后上方内容增高可能让阅读位置略有移动。

### 旧样式移除后的状态

共享主题、图片文件级布局覆盖和 `writer.json.style` 已移除；旧 `style` 读取忽略、正常保存不再写出，
不恢复这些能力，也不新增布局身份。正文、图注、图片引用与资源文件不受影响。

新的编辑环境设置及 PDF 配置实施前，编辑展示与导出使用各自默认参数，
Word / PDF 暂无字号、字体等输出调整入口。曾设置样式的旧项目外观会回到默认，旧设置不恢复。
这是直接取消旧样式的已接受结果，内容与结构不因此改变。

图片固有尺寸仍按固定 96 DPI 换算（与移除前相同）：高分辨率截图在输出中可能显得偏大，
由正文区宽 / 高上限兜底，不会溢出页面。DPI 策略待定（docs/decisions.md 第 8 节）。

PDF 的 PNG 无损编码使用本地 `krilla 0.8.2` 补丁，保留了上游源码与许可证。
升级 Typst / krilla 时须核对补丁或移除已被上游替代的实现，再运行通道往返、透明遮罩与 PDF 渲染对照；
具体范围与步骤见 `src-tauri/vendor/krilla/WRITER-PATCH.md`。
