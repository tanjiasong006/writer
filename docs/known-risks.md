# 长期风险与结论

本轮评估后决定暂不修改、但需要记录的三项风险。

## 1. 树操作递归，极深文档可能栈溢出（已解决）

> 已处理：Domain 引入 `MAX_CHAPTER_DEPTH = 32`。`validateTree` 超过上限即停止深入并报告
> `depth-exceeded`，移动与插入也不能产生超限的树，因此所有递归遍历的深度都有上界。
> 以下为原始记录。

`chapter_tree`、`chapter_numbering`、拖拽定位与渲染摊平都使用递归遍历。
正常导入的文档深度远达不到引擎调用栈上限，但恶意或异常深的导入数据理论上可能触发
`RangeError: Maximum call stack size exceeded`。

结论：本轮不重写全部树算法。后续接入文件导入时，优先在信任边界上：
- 把 `validateTree` 改成显式栈遍历，或
- 明确并验证一个最大章节深度，超限直接拒绝导入。

## 2. 章节重排只有鼠标拖拽（已解决）

> 已处理：选中章节可以用键盘上移 / 下移 / 提升 / 降级——章节获得焦点时按 Shift+F10（或菜单键）打开章节菜单选择，
> 或使用菜单栏"章节"中的同名命令。Application `keyboardMoveIntent` 把方向换算成与拖拽相同的 `MoveIntent`，
> 仍由 `moveChapterTo` 执行，没有新增移动规则。（早先的 Alt+Shift+方向键 快捷键已取消：Writer 的快捷键只用
> "⌘ + 一个键"，见 `src/ui/common/shortcuts.ts`。）以下为原始记录。

`ChapterTree` 仅实现 HTML5 拖拽，键盘用户无法重排章节。

结论：本轮不实现。做可访问性时，为选中章节增加「上移 / 下移 / 提升 / 降级」快捷键，
复用 Application 的 `moveChapterTo`，不新增移动规则。

## 3. 折叠状态只按章节 ID 保存（已解决）

> 已处理：折叠状态由工作区按项目持有（保存在各项目的 `.writer/ui-state.json`），
> 切换项目时工作区整体重建，不会继承上一份文档的折叠状态。以下为原始记录。

`ChapterTree` 的 `collapsedIds` 只有章节 ID。未来支持多文档时，不同文档里相同的
章节 ID 会继承上一份文档的折叠状态。

结论：本轮只有一个文档来源，不处理。引入多文档后，把折叠状态的键改为
「文档 ID + 章节 ID」，或在切换文档时清空 `collapsedIds`。

## 4. 外部程序修改项目文件

Writer 打开项目时把全部正文读入内存。打开期间如果用其他编辑器修改了某章节的 `content/*.md`：
- 该章节在 Writer 中未被编辑 → 换名时按字节保留磁盘上的版本，外部修改不丢；
- 该章节在 Writer 中也被编辑 → Writer 保存时以自己的版本覆盖。

结论：MVP 不做文件监听与冲突合并。同一时间只在 Writer 中编辑；多个 Writer 进程由项目独占锁（`.writer/lock`）阻止。

## 5. 真实桌面环境的端到端验证

自动化测试覆盖了 Domain / Application / UI（内存存储）与 Rust 存储 / 渲染 / 导出，
但原生对话框、窗口关闭 / 退出流程、Word 中的最终排版需要在真实桌面环境中手动核对。

结论：每次发布前按 `docs/implementation-plan.md` 的"手动验收清单"执行一遍。

## 6. 安装包体积

内嵌 Typst 后 release 可执行文件约 46 MB（gzip 后约 21 MB），其中 Typst 内嵌字体约 9.6 MB。

结论：可接受。若需要缩小，可去掉 `typst-kit` 的 `embedded-fonts`，完全依赖系统拉丁字体。

## 7. 结构化编辑与 Markdown 表达能力

正文以 Markdown 保存，编辑器中的结构必须能写回 Markdown。只有被编辑过的章节会重新写出，此时：

- 强调（粗体 / 斜体 / 删除线）边界紧挨中文标点、外侧紧挨文字时（是**“重要”**的），CommonMark 规则下会变成字面星号。
  写出时把边界上的标点移到标记外（是“**重要**”的）；极少数相邻多重强调仍无法表达时去掉该处格式。文字本身永远不变。
- 未被使用的链接引用定义（`[x]: url`，包括写成这种形式的脚注定义）在渲染结果中本来就不可见，编辑该章节后会被去掉；
  引用式链接改写为行内链接。
- 原始 HTML 在预览 / 导出中本来就显示为文字，编辑后以转义后的文字保存。
- 行首空白、空段落、段首段尾的硬换行在 Markdown 中不显示，写出时去掉；列表的紧凑 / 松散按 Markdown 规则确定。
- 块级嵌套达到 100 层的内容（远超 Rust 渲染器的 32 层）在编辑器中无法完整表示，编辑该章节会丢失超出的部分。

结论：以上都是 Markdown 本身的表达限制，渲染结果（预览 / Word / PDF）与编辑器所见一致；不为此改变存储格式。

## 8. 文档样式的已知限制

- 图片布局是图片文件（asset）级的布局覆盖，按"图片文件键"（引用指向的文件）保存，不是元素实例身份：
  同一个文件在文档中出现多次时共享同一个布局。这让剪切粘贴、跨章节移动、撤销删除后布局都能保留。
  再次插入同名且内容相同的文件会复用同一个资源（因此共享布局）；需要不同布局时，只能先把源文件另存为不同的文件名再插入。
- 用户只能在宋体类 / 黑体类之间选择字体。楷体、仿宋等在 macOS 上不是默认安装的字体，PDF 无法可靠输出，暂不提供。
- Word 只写字体名（宋体类：Times New Roman + SimSun；黑体类：Arial + SimHei），实际字形由打开文档的机器决定。
- 编辑器 / 预览的版心（约 522 磅）比 A4 正文宽度（约 453 磅）宽，折行位置不同；字号、行距、段距、标题层级、
  图片占正文宽度的比例是一致的。
- 不认识 `style` 的旧版 Writer 可以打开新项目，但保存时会丢弃样式（正文不受影响）。不为此升级 `version`：
  它只能让旧版拒绝打开，会连正文编辑一起挡住（见 docs/project-format.md 第 3.1 节）。

结论：以上都不影响正文数据；需要时分别评估"元素实例级的稳定身份（单独设计，不扩展 Markdown）""打包开源中文字体""按纸张宽度显示版心"。
